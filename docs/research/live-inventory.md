## Corrections — read before the generated verdicts below

The script's raw responses are sound; three of its **auto-generated verdicts are not**,
and each was resolved by a follow-up probe. Where this section and a verdict below
disagree, this section wins.

**Unknown 6 — "capped at 991 returned items" is wrong, and the paging advice under it is
dangerous.** 991 is not a ceiling and not a total. `$top=1000` returned 991, and
`$skip=1000` then returned **another 985** — so the org holds at least 1,976 PRs and the
endpoint hands back *fewer rows than requested while more still exist*. The same shortfall
appears at every size: 500→497, 100→100 but `$skip=100`→98. The service is filtering after
applying `$top`. The real finding is two-part: **`$top` clamps at 1000** (2000 and 5000
silently return the identical 991), and **a short page is not the last page** — the exact
opposite of the generated text's "page until `count < $top`… that logic is correct either
way". Stop only on an *empty* page, advance `$skip` by the *requested* `$top`, and dedupe
by `pullRequestId`, since whether `$skip` applies before or after the filter is unresolved.

**Unknown 4 — the "unauthenticated GET → 302" row is note 4, not evidence.** The script
omits `X-TFS-FedAuthRedirect: Suppress` on its anonymous probe, so it measured the
sign-in redirect rather than the route. Re-probed properly, the discriminator is clean and
the conclusion holds for a better reason: anonymous+Suppress → **401**, authenticated →
**200 `{"count":0,"value":[]}`**, and an invented sibling path → **404**. The likes route
exists and reads. Writability remains unproven — that needs a PUT against a real
colleague's comment.

**Unknown 2 — the verdict is right; its most important line is wrong.** "Batched
`rules/search` returned descriptions: **false**" was a bad parameter name, not a service
limitation. The parameter is **`rule_keys`**, plural — and `rule_key` doesn't error, it
silently returns `total: 0`, so the mistake reads as "no such rules". With `rule_keys`:
`total: 3`, all three carrying `htmlDesc`. The one-request-warms-every-rule-in-a-PR plan
is intact.
